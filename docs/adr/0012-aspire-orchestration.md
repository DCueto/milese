# .NET Aspire orchestrates local development

`apps/api` gains three projects — `Aspire.AppHost`, `Aspire.ServiceDefaults`, `Aspire.MigrationService` — mirroring `iplan-nexus-core`'s harness. The AppHost starts a Postgres container, waits for the MigrationService to apply migrations, then starts `Api.Rest` wired to it via service discovery (`AddNpgsqlDbContext<MileseDbContext>("milesedb", ...)`); `ServiceDefaults` adds health checks, OpenTelemetry, and resilience handlers to `Api.Rest` for free. `Api.Rest` still runs standalone against a manually-run Postgres container (`dotnet-stack`-style) when Aspire's overhead isn't wanted — Aspire only changes how the API host is *composed*, not how it's *deployable*.

**Consequences:** three more projects and a NuGet-resolved MSBuild SDK (`Aspire.AppHost.Sdk`) for a currently solo project — accepted because it buys a one-command local loop (`dotnet run` on the AppHost) now, before `apps/web`/`apps/mobile` and any future services (e.g. an embeddings worker for the Tutor) make manual multi-process orchestration painful; per [docs/adr/0010](./0010-postgres-hosting-open.md), general hosting stays undecided, and Aspire's production deployment story (`azd`, manifest export) is explicitly out of scope until that's chosen.
