# UserId is a sequential int, not a Guid, despite being personal data

`UserId` follows the existing per-entity Id pattern (`TrackId`, `SubjectId`, `ConceptId`, `LessonId` are all sequential ints) rather than a Guid. This was a deliberate override of the initially-recommended choice: unlike a Track or Lesson id, a `UserId` is tied to one person's private progress data, so a sequential int lets `/api/learners/2`-style enumeration be attempted against another Learner's data — a Guid would have closed that off by making the id unguessable. The founder chose consistency with the existing Id pattern over that hardening for the MVP.

**Consequences:** endpoints that take a `UserId` (or infer it from the caller's claims) must authorize on *identity*, not just *authentication* — a valid token for Learner A must never be allowed to read/write Learner B's data by guessing B's id. This matters more here than it would with a Guid, since the id itself offers no obfuscation. Since `EntraObjectId` (a Guid) is a separate field used only to resolve the caller's own `UserId` at sign-in, revisiting this later (switching `UserId` to a Guid) is a schema change but not an identity-provider migration.
