# Scaffold apps/web and apps/mobile, integrated with the Auth backend

## Problem Statement

Neither `apps/web` nor `apps/mobile` exist yet — Milese has a backend (Curriculum, and soon Auth) but no way for a Learner to actually use it. None of the client-side architecture already decided (ADR-0017 through ADR-0030: state, forms, testing, styling, UI primitives, animation, API client, i18n, navigation) has been built or proven against a real app.

## Solution

Scaffold both apps from scratch with the full decided stack, wire both to the Auth backend (Entra External ID via `@azure/msal-react` on web, `expo-auth-session` on mobile) and to `apps/api` via the shared `openapi-typescript`-generated types package, and prove the whole thing actually works with one end-to-end smoke test per platform against the real, Aspire-orchestrated API — sign in, call a real protected endpoint, render the response.

## User Stories

1. As a developer, I want `apps/web`, `apps/mobile`, and a shared generated-types package under one pnpm workspace, so that both apps consume the same API types without duplicating them.
2. As a developer, I want the shared types package generated by `openapi-typescript` from `apps/api`'s live OpenAPI spec, so that a backend contract change is caught as a type error in either client rather than discovered at runtime.
3. As a developer, I want a documented (or scripted) way to regenerate the shared types whenever `apps/api`'s OpenAPI spec changes, so the types don't silently drift from the real backend.
4. As a Learner, I want to open `apps/web` and see a sign-in screen, so that I understand I need to sign in before using the app.
5. As a Learner, I want to sign in on web via Entra's hosted login page federated to Google, so that I use my existing Google account.
6. As a Learner, I want my session to persist across a page reload on web (MSAL's token cache), so that I'm not forced to sign in again every time I refresh.
7. As a developer, I want `apps/web`'s API calls to attach the current access token as a Bearer header automatically (via `openapi-fetch`, acquiring silently through MSAL), so that no component has to manually manage the token.
8. As a Learner, I want at least one real screen after signing in on web that calls a real protected `apps/api` endpoint and renders the result, so that the whole stack (auth, API client, rendering) is proven end-to-end, not just scaffolded.
9. As a developer, I want `apps/web` built with Next.js's App Router and TypeScript, styled with Tailwind CSS, so that it matches the decided stack.
10. As a developer, I want interactive components (at minimum whatever the sign-in screen needs) built on shadcn/ui over Radix primitives, so that accessibility behavior (focus, keyboard nav) isn't hand-rolled.
11. As a developer, I want at least one element on web using Motion, so that the animation pipeline (for future progress rings/streaks/unlock animations) is proven wired, not just installed.
12. As a Learner, I want the web app's UI text to render in Spanish or English via next-intl, so that Content Language support (ADR-0011) extends to the app shell, not just Lesson content.
13. As a developer, I want Zustand available for client/UI state and TanStack Query available for server state on web, so that the state-management pattern (ADR-0017) is wired and ready for the first real feature that needs it.
14. As a developer, I want React Hook Form + Zod available and demonstrated (even if no real user-facing form exists yet at scaffold time), so that the forms pattern (ADR-0018) is proven to work with this specific app setup before the first real form is built.
15. As a developer, I want a Vitest setup for web unit/component tests, so that future components have a test runner ready without additional setup.
16. As a developer, I want a Playwright e2e suite for web that signs in by injecting a pre-acquired token into browser storage (never driving the real Google/Entra login UI), so that e2e tests are fast and don't depend on external UI stability.
17. As a Learner, I want to open `apps/mobile` on Android and see a sign-in screen, so that mobile has the same entry experience as web.
18. As a Learner, I want to sign in on mobile via the same Entra/Google browser-delegated flow, so that my identity is the same person whether I use web or mobile.
19. As a Learner, I want my mobile session token stored securely on-device (`expo-secure-store`), so that it survives closing and reopening the app without being stored insecurely.
20. As a developer, I want `apps/mobile`'s API calls to attach the stored access token as a Bearer header automatically, mirroring web's pattern, using the same shared generated types.
21. As a Learner, I want at least one real screen after signing in on mobile that calls a real protected `apps/api` endpoint and renders the result, proving the same end-to-end stack works on mobile as on web.
22. As a developer, I want `apps/mobile` built with Expo Router and NativeWind (its own local Tailwind config, not shared with web per ADR-0023), so that navigation and styling match the decided stack.
23. As a developer, I want Reanimated + `react-native-svg` wired with at least one animated element (e.g. a placeholder progress ring), so that the animation/graphics pipeline is proven working before the first real gamification screen is built.
24. As a developer, I want a Jest + React Native Testing Library setup for mobile unit/component tests, so that future components have a test runner ready.
25. As a developer, I want a Maestro e2e flow for mobile that signs in via an injected pre-acquired token (never driving the real Google/Entra login UI), mirroring web's Playwright approach.
26. As a developer, I want `apps/mobile` configured for Expo's managed workflow with an EAS development build profile (not Expo Go), since a development build is what a custom Entra redirect URI actually needs to work.
27. As a developer, I want both apps' e2e suites to run against a real, running `apps/api` (via the Aspire AppHost) rather than a mocked API layer, so that integration/contract drift is actually caught, consistent with how the rest of this codebase tests.

## Implementation Decisions

- **Monorepo layout**: `apps/web`, `apps/mobile`, and a new shared package (generated API types) all live under a pnpm workspace (ADR-0021) rooted at the repo root, alongside the existing `apps/api`.
- **Shared types package**: generated by `openapi-typescript` against `apps/api`'s live OpenAPI spec (already exposed via `MapOpenApi()` in Development, per the earlier Scalar/OpenAPI work). The generated output is committed as regular generated code, regenerated on demand when the backend's contract changes — not hand-edited.
- **Web stack**: Next.js (App Router) + TypeScript, Tailwind CSS (ADR-0026), shadcn/ui on Radix (ADR-0027) for interactive components, Motion (ADR-0028) for animation, `openapi-fetch` (ADR-0029) as the typed HTTP client wired into TanStack Query, Zustand for UI state (ADR-0017), React Hook Form + Zod (ADR-0018), next-intl (ADR-0030) with Spanish and English message catalogs (ADR-0011), `@azure/msal-browser` + `@azure/msal-react` (ADR-0020) with `MsalProvider` at the app root.
- **Mobile stack**: Expo (managed workflow, Android target, EAS development build profile — Expo Go isn't sufficient for a custom Entra redirect URI), Expo Router (ADR-0022), NativeWind with its own local Tailwind config (ADR-0023 — explicitly not shared with web's config), Reanimated + `react-native-svg` (ADR-0024), `expo-auth-session` for the browser-delegated Entra flow + `expo-secure-store` for token persistence, the same shared generated-types package consumed through a thin `fetch` wrapper (mirroring web's `openapi-fetch` pattern), Zustand + TanStack Query, React Hook Form + Zod, Jest + React Native Testing Library (ADR-0025).
- **Minimal vertical slice, not real features**: each app's scaffold includes exactly one sign-in screen and one authenticated screen that calls a real protected `apps/api` endpoint (e.g. the existing `GET /api/lessons`) and renders something from the response. This is the smallest possible proof that auth, the typed API client, and rendering all actually work together — not a real Curriculum-browsing or gamification screen.
- **Entra app registration needs redirect URIs for both platforms** (a web redirect URI for `apps/web`, a custom-scheme/dev-build redirect for `apps/mobile`) — configured as part of the same Entra-portal provisioning step already flagged in the `auth-backend` spec as a human, out-of-scope-for-agents task.

## Testing Decisions

- **Primary seam: one e2e smoke test per platform** (Playwright for web, Maestro for mobile), run against the real, Aspire-orchestrated `apps/api` — confirmed with the founder over mocking the API, consistent with this codebase's existing testing philosophy (real database/pipeline, never mocked business logic). Each smoke test: launch the app → inject a pre-acquired token (never drive the real Google/Entra login UI) → hit the one authenticated screen → assert the real API response rendered.
- **Component-level tests** (Vitest on web, Jest + RN Testing Library on mobile) cover individual pieces as they're built during scaffolding (e.g. the sign-in screen's rendering, a form validation rule) — not exhaustive at scaffold time, since there's minimal business logic yet beyond the vertical slice.
- **Scaffolding/tooling configuration itself is not unit-tested** (nobody tests that Tailwind is installed) — its correctness is proven by the e2e smoke test actually passing against the real backend.
- **No existing client-side test to reuse as prior art** — both apps are new. Prior art instead comes from the backend's own testing philosophy (real integration over mocks) applied here, and from each library's documented testing conventions (MSAL React's test utilities, React Native Testing Library's standard patterns) for the component-level tests.

## Out of Scope

- The Auth backend itself (`apps/api`) — covered by the separate `auth-backend` spec; this spec assumes it exists and is running.
- Any real Milese feature screens beyond the minimal sign-in + one-authenticated-screen slice needed to prove the stack (no real Curriculum-browsing UI, no Progress/gamification UI — those are future specs).
- iOS build/config (Android-only, per the earlier scope decision).
- A shared Tailwind/design-tokens package between web and mobile (explicitly rejected, ADR-0023).
- CI pipeline wiring for either app's test suites (a future concern once there's a CI story for the JS/TS side of the monorepo).

## Further Notes

Backed by ADR-0017 through ADR-0030, plus ADR-0014/0015/0016 (Entra External ID, `UserId` shape, Bearer-everywhere) from the `auth-backend` spec, which this spec's clients integrate against but do not redesign.

This spec's tickets depend on `auth-backend`'s tickets landing (or at least being runnable) before its e2e smoke tests can pass for real — `/to-tickets` should mark the relevant tickets here as blocked-by the `auth-backend` ticket(s) that stand up token validation and the dev/test auth seams.
